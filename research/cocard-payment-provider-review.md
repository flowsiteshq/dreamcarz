# CoCard payment-provider assessment

## Current finding

The supplied URL, `https://secure.cocardgateway.com/merchants/`, redirects to a merchant-control-panel login. It does not expose public API documentation, hosted-payment fields, tokenization details, callback documentation, or a sandbox endpoint. No login attempt, payment action, credential entry, or transaction creation was performed.

CoCard’s public site describes the organization as an independent sales organization and lists relationships with several processing platforms, rather than identifying the exact gateway configuration assigned to DreamCarz. It therefore does not establish which API, vault/token, hosted-checkout, recurring-billing, authorization, refund, or event-notification capability is enabled for this merchant account. [1]

The authenticated DreamCarz CoCard gateway portal was inspected on 2026-08-29. Its Developer Docs expose **Collect.js**, **Collect Checkout**, **Payment API**, **Three Step Redirect API**, **Gateway.js**, **Webhooks**, and **Query API**. The portal describes Collect.js as a gateway-hosted popup that returns a token for use with the Payment API while keeping raw card/bank data off the merchant site. It describes Collect Checkout as a gateway-hosted checkout page that keeps payment data entirely on gateway servers. The portal also lists gateway endpoints compatible with Authorize.Net-style AIM/SIM submissions and documentation for customer-vault and recurring-subscription actions through its Sparrow emulator. These findings establish that DreamCarz can use a CoCard-hosted/tokenized surface rather than receiving card data directly.

The Collect Checkout methodology was also reviewed in the authenticated portal. It describes a customer path in which DreamCarz renders a payment trigger, CoCard loads the hosted checkout, the customer sees the selected products and total, and the browser returns to DreamCarz only after a successful transaction. DreamCarz should use this hosted path for approved membership, rental, deposit, or purchase amounts; payment form elements stay on CoCard servers. The implementation will not enable the trigger until the exact Collect Checkout integration parameters, server-side authorization method, callback verification rules, and approved transaction amounts are configured.

The authenticated Collect Checkout integration reference specifies a `CollectCheckout.redirectToCheckout(options)` launch model. It accepts line items, with either merchant-created product SKUs or custom-payment descriptions/currency, and supports payment types including `sale`, `auth`, and `customerVaultOnly`. It also documents optional customer-vault creation. DreamCarz will use a gateway-hosted `auth` or `customerVaultOnly` configuration only after the documented production checkout key, merchant-owned product/amount record, return allowlist, and callback-verification design are configured. The browser must never receive a server-side security key, and DreamCarz will never place raw card fields in the application.

The Collect Checkout reference also documents `successUrl` and `cancelUrl` browser return locations, optional receipt behavior, and a gateway requirement that SKU-based line items already exist in the merchant account’s Product Manager. It permits a custom-payment line item with a merchant-controlled description and currency, but that path must never permit a customer to choose a vehicle price, deposit, or down-payment amount. DreamCarz will form the checkout request only from an administrator-approved pricing snapshot and will use the protected transaction reference as the internal correlation value. Gateway results must still be reconciled through an authenticated server-side verification or documented signed callback before any lifecycle status changes.

The CoCard webhook setup documentation requires an HTTPS POST receiver and provides a per-endpoint signing key. It documents a `webhook-signature` header formatted as a nonce and signature, with verification based on an HMAC-SHA256 of `nonce + webhookBody` using that signing key. It also recommends restricting inbound requests to the documented gateway IP ranges. DreamCarz will implement constant-time HMAC verification, reject unsigned/malformed callbacks, deduplicate provider events, and store only minimized transaction identifiers and event outcomes. The signing key will be stored solely as a protected server secret after the customer authorizes endpoint configuration.

The CoCard events reference lists transaction events for sales, authorizations, captures, voids, refunds, and credits, each with successful, failed, or unknown outcomes. It also lists recurring-payment, batch, chargeback, and automatic-card-updater event categories. DreamCarz will subscribe only to the transaction and chargeback event families necessary for the applicable lifecycle and will map a verified authorization, capture, failure, void, refund, or chargeback to the corresponding transaction event and manual-review state. It will not treat a browser return URL as evidence of payment success.

The CoCard `transaction.sale.success` webhook example identifies the delivery with a top-level `event_id` and `event_type`, then provides a nested `event_body` containing gateway `transaction_id`, `transaction_type`, `condition`, `processor_id`, `order_id`, `customer_id`, `customer_vault_id`, and `authorization_code` fields. DreamCarz will use CoCard `event_id` for idempotency and store only gateway identifiers and the resulting status. Because the Collect Checkout reference does not document a merchant `order_id` option, DreamCarz will correlate the payment safely through its account-owned, allowlisted return URL plus a subsequent verified gateway event or server-side Query API confirmation. It will not persist the delivered payment/customer payload, billing address, or payment-account fields.

CoCard's Collect Checkout success-return documentation supports `(TRANSACTION_ID)` and `(CUSTOMER_VAULT_ID)` placeholders in an allowlisted HTTPS `successUrl`. It cautions that a customer browser return does not prove a transaction’s validity or uniqueness and recommends querying the gateway server-side before any goods or services are released. DreamCarz will use an account-owned return URL containing the existing protected transaction reference plus the gateway transaction placeholder, record it only as a reconciliation candidate, and require a verified gateway event or server-side query before it marks payment authorized or paid.

## DreamCarz integration boundary

DreamCarz will remove the unused Stripe payment path and build a CoCard adapter around **Collect Checkout** or **Collect.js**. The application must direct a customer to a gateway-hosted payment or tokenization surface, so that DreamCarz never receives, logs, stores, or displays a PAN, CVV, magnetic-stripe data, or card-expiration value. DreamCarz should retain only gateway-approved identifier references, lifecycle status, and an immutable audit event.

Payment authorization and a later capture/settlement must remain distinct. No deposit, rental charge, purchase down payment, membership charge, recurring charge, or refund will be attempted until the merchant’s enabled CoCard interface, secure server credential method, callback/signature verification method, and approved transaction-specific pricing are confirmed.

## Required merchant-side information

The implementation needs confirmation of the selected **Collect Checkout** or **Collect.js** route, the corresponding developer specification and production settings, a **sandbox/test profile** if available, the **server credential delivery method**, an **event/callback signature specification**, and the authorized production callback URL. The merchant portal’s documented access key and security key must be entered only through the protected configuration flow—not in chat or source code.
